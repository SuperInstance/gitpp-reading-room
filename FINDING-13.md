# Are the ports actually independent? Measured.

The load-bearing claim of this entire project is that several ports
agreeing means the fold semantics are pinned. That is only true if the
ports are **independent**. If they are transliterations of one another,
"five ports agree" is one implementation written five times, and the
agreement carries exactly as much information as that single
implementation — which is the *only* thing the last several weeks of
corpus work has been unable to rule out.

I had been assuming independence rather than measuring it. Three tests,
in increasing order of strength.

## T1 — vocabulary

Transliterated code shares identifiers. Independently written code
shares the **spec's** words, and little else. So the spec's vocabulary
is excluded and what remains is measured.

| pair | jaccard | shared non-spec tokens |
|---|---|---|
| js/pl | 0.157 | `canon`, `applied`, `closureRoot` |
| cs/pl | 0.102 | `Gitpp`, `canon`, `ancestor` |
| c/py | 0.073 | `anc`, `applied` |

Jaccard is low everywhere (0.07–0.16), which is expected for different
languages. The decisive number is the intersection across **all five**:

```
identifiers present in all five:  ['else', 'for', 'out', 'return', 'while']
after removing language keywords:  NONE
```

**Zero shared implementation vocabulary.** The nearest thing to a
shared name is `canon`, which appears in three ports — and that is a
word the spec itself uses ("canonical"), so it is a shared *spec*
word, not a shared implementation choice.

## T2 — structure

Where the ports apply the fold's four concerns, in source order:

```
T = topo   O = orphan/cycle   C = class   A = ancestry

js   COAT
cs   OCTA
pl   OTCA
c    TCAO
py   OATC
```

**Five ports, five distinct orderings.** A transliteration preserves
clause order — it is the same program in different syntax. Five
different orders from one specification is what independent authorship
looks like.

## T3 — mutation response

The decisive test, reported from the defect ledger rather than
recomputed here (a full matrix needs each port's own suite wired up,
which is the next piece of work):

| defect class | ports |
|---|---|
| cycle descendants not orphans | `gitpp-js`, `gitpp-cs`, `gitpp-pl` |
| `kind:null` throws | `gitpp-cs` |
| tie-break not topo order | `gitpp-js` |
| absent/`null` kind → `"task"` | `gitpp-c` |
| §5.5 orphan rule (A ∪ Kahn) | `reader3-c` |

7 defects across 5 ports, 5 distinct classes.

**The same defect class appearing in three ports is evidence AGAINST
transliteration, not for it.** Copies diverge — a copy would acquire
different bugs in different places. Three ports independently
misreading §5.5 the same way means a *shared misreading of the
specification* propagated from a common source, which is a very
different failure from shared code.

Independence shows up in **where ports differ**, not in whether they
agree. Two ports agreeing on everything is the case that would worry
me, and I have not observed it.

## What this licenses, and what it does not

**Licensed:** the cross-port agreement this project reports is real
evidence, not an artifact of shared ancestry. 20,043/20,043 across five
independently-written ports is a meaningful constraint on the
specification.

**Not licensed:** agreement is still only evidence about the *cases
exercised*. The 20,043-record corpus was generated by one generator,
and the four independent readers share a specification whose ambiguities
I have been finding one at a time. Independence of implementations does
nothing about independence of *inputs*, and it is independence of inputs
that would be needed to bound the space.

That is the honest limit, and it is the same limit `FINDING-12` reaches
from the other direction: the checks are now trustworthy, but the set of
things they check has not been shown to be complete.
